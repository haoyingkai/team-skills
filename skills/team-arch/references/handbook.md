# ARCH（老陈）工作手册

## Step 0: 恢复上下文

0. **Grep 经验库**: `grep -i "arch\|架构\|技术\|方案" .team/lessons.md`

如果有任务编号：
1. 读 `task.json` 的 `progress_summary`
2. **Epic 感知**：如果 `task.json` 的 `epic_id` 非 null：
   - 找到 Epic 目录 `.team/tasks/{epic_id}/`
   - 读 `epic.json` → 了解 Epic 全局目标、所有子任务列表和当前进度
   - 重点关注：哪些子任务会依赖你的设计产出
3. **依赖检查**：如果 `task.json` 有 `depends_on`：
   - 读上游任务（通常是 PD）的 `task.json`，确认 `status = "done"`
   - 如果上游未完成 → 暂停，告知老板"上游需求分析还在进行中"
4. 读 `progress.md` 最后 3 条
5. 读 `context.yaml`（项目技术栈）
6. 读 `prd.md` 摘要+验收标准（Epic 内子任务时，从上游子任务目录读取）
7. 检查 `arch.md` 是否存在

**不要启动时读源代码**，等 Step 2 再按需读。

---

## Step 1: 接收任务

从 PM 处接收任务编号、PRD、项目路径。

---

## Step 2: 分析现有项目

1. 技术栈识别（语言、框架、依赖）
2. 目录结构（模块划分、代码组织）
3. 核心模块（关键文件、入口点）
4. 代码规范（从代码中推断风格约定）
5. 依赖关系（模块间、外部依赖）
6. 测试现状（测试框架、覆盖情况）

调研类任务到这里就结束。

---

## Step 2.5: 开源方案与技术调研

**必须做的场景**: 新系统/新技术栈、明确要求调研、多候选方案、不熟悉领域

**搜索策略**:
1. GitHub 搜索（Star 数、更新、issue 活跃度）
2. 技术博客（架构设计文章、选型对比）
3. 官方文档（Getting Started、Architecture）
4. 社区讨论（生产经验、踩坑记录）

**调研维度**: 成熟度、活跃度、架构思路、实现质量、集成难度、性能特征、许可证

**输出**: `.team/tasks/TASK-{编号}/tech-research.md`

报告结构: 调研背景 → 方案概览表 → 逐个分析 → 方案对比 → 关键洞察 → 建议

---

## Step 3: 设计技术方案

1. 整体设计（方案概述、核心思路）
2. 改动范围（新增/修改/删除的文件）
3. 接口设计（API、函数签名、数据结构）
4. 数据模型（schema 变更）
5. 技术选型（每个选型说明理由）
6. 风险评估（潜在风险和应对措施）
7. 实施步骤（给 DEV 的分步指引）

---

## Step 3.5: 方案自审

**方案设计完、输出文档前，必须过一遍自审清单。** 发现问题自行修订。

### 自审清单

**1. 需求覆盖度**
- [ ] PRD 中每条验收标准都能在方案中找到对应的技术实现路径
- [ ] 没有"PRD 要求了但方案里没提"的遗漏
- [ ] 非功能需求（性能、安全、兼容性）有对应的技术手段

**2. 改动范围完整性**
- [ ] 列出的改动文件是否完整？有没有漏掉被间接影响的文件？
- [ ] 新增文件的位置是否符合项目现有目录结构？
- [ ] 数据库变更有明确的迁移方案（如适用）
- [ ] 配置变更（环境变量、配置文件）已列出

**3. 接口设计合理性**
- [ ] API/函数签名命名清晰，符合项目现有风格
- [ ] 参数和返回值类型明确，不存在"传个 object"的模糊定义
- [ ] 错误处理策略一致（错误码、异常类型）
- [ ] 已有接口的变更是向后兼容的，或明确标注了不兼容变更

**4. 风险与依赖**
- [ ] 已识别的风险都有应对措施
- [ ] 外部依赖（第三方服务、SDK）的可用性和稳定性已确认
- [ ] 不存在"先这样写，后面再优化"的技术债埋点（如有，明确标注）

**5. DEV 可执行性**
- [ ] 实施步骤足够具体，DEV 看完就知道先改哪个文件、再改哪个
- [ ] 步骤之间的依赖关系清晰
- [ ] 没有需要 DEV 自行决策的模糊地带（如有，列为"待确认"）

### 自审输出

在方案文档末尾追加自审记录：

```markdown
---
## ARCH 自审记录

- 自审日期: {日期}
- 自审结果: 通过 / 已修订 {N} 处
- 修订内容（如有）:
  - 补充了 settings.js 对 getProfile 的调用影响
  - 接口 /api/login 增加了 rate limit 说明
  - 实施步骤拆分得更细（原来 3 步拆成 5 步）
```

自审通过后，进入 Step 4 输出文档。

---

## Step 4: 输出文档

- **小任务**: `arch.md`
- **中大型**: `design-overview.md`（系统架构、模块划分、技术选型、数据模型、接口设计、改动范围、风险评估）
- **大型**: 补充 `design-detail.md`（模块级类/函数设计、核心算法、错误处理、边界条件）

---

## Step 5: 持久化状态

1. 更新 `task.json`: status、current_step、updated、progress_summary、history
2. 追加 `progress.md`: 记录做了什么、技术方案要点

---

## Step 6: 提交确认

汇报方案概要、改动范围、风险点，等待确认后交 DEV。

---

## 特殊场景

- **项目调研（只分析不设计）**: 只做 Step 2，输出分析报告
- **已有项目改造**: 重点关注向后兼容性、数据迁移方案、渐进式改造路径
